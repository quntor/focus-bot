# Голосовой и текстовый список задач

## Проблема

Сейчас свободный текст воспринимается только как намерение одной сессии, а
голосовые сообщения webhook игнорирует. Пользователь не может одной фразой
зафиксировать несколько дел на день, выбрать одно из списка или сказать:
«эту задачу сделал, приступаю к следующей».

## Решение MVP

Один общий контур обрабатывает и текст, и расшифрованный голос:

1. Telegram voice скачивается в память с жёсткими лимитами и передаётся во
   внутреннюю модель `openai/whisper-large-v3` в Cloud.ru с явным `language=ru`
   и коротким словарём продуктовых терминов (`Милавица`, `VDS`, `FocusBot`),
   чтобы модель не переводила русскую речь в английский и реже искажала названия.
2. Аудио не пишется на диск и не сохраняется в БД. Пользователь видит
   полученную расшифровку.
3. GigaChat получает расшифровку или исходный текст и активные задачи только
   этого пользователя под временными метками `t1..t20`.
4. Строгий JSON-ответ выбирает одно из трёх действий:
   - обычное намерение одной сессии;
   - добавить от одной до десяти задач;
   - завершить существующую задачу и начать существующую или новую.
   Для списка каждое явно названное самостоятельное действие сохраняется ровно
   один раз; близкие переформулировки одного действия объединяются в более
   конкретное название, а разные действия над одним объектом не склеиваются.
5. Код проверяет схему, переводит временные метки в ID и сам выполняет записи.
   Модель не получает ID из БД и не может вызвать действие напрямую.
   Если первый ответ нарушил JSON-схему, parser делает ровно одну повторную
   попытку с усиленным требованием типов в пределах общего 8-секундного бюджета;
   ошибки API и timeout не повторяются.
   После валидации код консервативно объединяет только названия с тем же
   действием и почти одинаковым объектом.

После добавления бот показывает активные задачи inline-кнопками. Выбор задачи
запускает обычную сессию с действующим правилом длительности. Явная фраза
«сделал X и приступаю к Y» завершает текущую running-сессию как `done`, отмечает
X выполненной и без отдыха запускает Y. Для paused-сессии автоматическое
переключение не выполняется: сначала нужно вернуться к работе.

## Почему так

### Выбрано: Whisper → текст → GigaChat → строгие действия кода

- один и тот же смысловой парсер для голоса и текста;
- можно показать и проверить расшифровку;
- аудио и продуктовую логику легко тестировать отдельно;
- Whisper размещён внутри Cloud.ru и доступен текущему сервисному ключу;
- ошибки STT не превращаются незаметно в операции с задачами.

### Не выбрано: мультимодальная модель сразу превращает аудио в действия

Сложнее отделить ошибку распознавания от ошибки разбора, выше стоимость,
доступные модели внешние, а тесты и fallback хуже.

### Не выбрано: локальный Whisper на VDS

Текущий VDS — 1 vCPU / 2 ГБ RAM. Локальное распознавание добавляет тяжёлую
модель, задержки и операционную нагрузку ради объёма, который на MVP дешевле
обработать по API.

## Границы и безопасность

- только личные чаты и пользователь с принятым согласием;
- voice: не больше 180 секунд и 5 МБ; Telegram Bot API дополнительно ограничивает
  скачивание 20 МБ;
- не больше пяти платных распознаваний на пользователя в час; шестое блокируется
  до скачивания файла и вызова STT;
- до десяти задач за сообщение, название до 80 символов;
- все чтения и записи фильтруются по `userId` из проверенного Telegram `from.id`;
- callback содержит только указатель; владение задачей повторно проверяется в БД;
- выдуманная или чужая метка модели отклоняется;
- при сбое STT аудио не передаётся в текстовый парсер, пользователю предлагается
  повторить или прислать текст;
- в событиях сохраняются длительность, длина и число задач, но не аудио и не
  полный текст расшифровки.

## Совместимость и конфигурация

- текст без явных признаков управления списком продолжает старый сценарий
  намерения сессии;
- STT включается только при заданном `STT_MODEL`; используется тот же
  `LLM_BASE_URL` и `LLM_API_KEY`;
- без STT текстовые задачи работают, voice получает понятный отказ;
- новая миграция не требуется: существующей модели `Task` достаточно.

## Приёмка

1. «Сегодня хочу сделать A, B и C» создаёт три активные задачи и показывает их
   кнопками выбора.
2. «Просто добавь задачу A» создаёт одну задачу; повтор не создаёт точный дубль.
3. Voice проходит `getFile` → download → Whisper → тот же разбор; аудио не
   сохраняется.
4. Нажатие задачи запускает сессию именно с ней; чужой task ID не работает.
5. «Эту сделал, приступаю к B» при running-сессии корректно закрывает текущую,
   отмечает её задачу `done` и запускает B.
6. Слишком длинный voice, выключенный STT, timeout и невалидный JSON дают
   безопасный ответ без частичных записей.
7. Существующие текстовые сценарии, таймеры, outbox и одна активная сессия не
   регрессируют.
8. Реальная проблемная фраза сохраняет «поправить все косяки», объединяет два
   варианта «планирования дня» и предпочитает написание `Милавица`, `VDS`,
   `FocusBot` без хранения пользовательской расшифровки в prompt.

## Выкатка и откат

Сначала код и миграционно нейтральные тесты, затем `STT_MODEL` в production env и
один ручной voice-smoke на командном аккаунте. Откат — убрать `STT_MODEL`:
текстовый контур останется рабочим, voice отключится без изменения данных.
